## Phase 8 — API and white-box testing (committed `007c0d5`)

**What it does**
- **Reads validation rules from the application's source code.**
  - Python is parsed properly (FastAPI/Flask routes, `if` checks, pydantic, marshmallow).
  - JavaScript/TypeScript is matched by pattern (zod, yup, joi, class-validator, Express routes).
  - Every rule cites the `file:line` it came from. Output: `test_comprehension/code_rules.json`.
- **Feeds those rules into test design.** Source-code rules rank below the BRD, the live UI and observed behaviour.
  Test cases built from a code rule carry the citation.
- **Generates API tests for every endpoint.** They cover: signed out, wrong role, someone else's record, wrong HTTP
  method, a valid request, each rule's boundary values, pagination, unusual query values, and repeat calls.
  - Tests that change data only run when the project allows destructive actions, outside production.
- **Checks the front end against the back end.** It flags:
  - a form with no matching route;
  - a field the server never reads;
  - a rule the browser enforces but the server does not.
- **Measures the app's code coverage (coverage.py, branch).**
  - Uncovered code is traced to the routes that reach it, and targeted "gap" tests are generated for those routes.
  - Measured coverage now appears in the report's coverage dashboard instead of "not measured".
- **Mutation testing.** It deliberately breaks conditions in chosen functions and checks that the tests notice. The
  original file is always restored, even after a crash.

## Phase 10 — Execution at scale (done; full write-up in `docs/phases/phase-10-report.md`)

| Item | What was built | Tested |
|---|---|---|
| 10.1 Burn-in admission | New and healed tests run 5 times before joining the regression suite. 5/5 passes → admitted; some passes → quarantined; 0 passes → left for triage. At most 50 specs per night. | Unit tests |
| 10.2 Flaky-test quarantine | `quarantine.yaml`: test, first seen, reason, failure signature, owner. Quarantined tests still run but never fail the quality gates. A test is released after 5 passes in a row. A test that is flaky twice is quarantined automatically. Shown in the HTML report. | Unit tests (round trip, release, reset, auto-add) |
| 10.3 Order independence | Each test runs three ways: normal, one file at a time in reverse order, and with 4 workers. A test that passes one way and fails another is marked `order_dependent`. | Unit tests |
| 10.4 Pre-run health check | Before tests run, it checks that the app answers, that each role's login session is still valid (refreshed once if expired), and that the required seed data exists. On failure the run is `environment_blocked` (exit code 3), not hundreds of failed tests. | Unit tests, plus a real run with the app down |
| 10.5 Selective execution | A fingerprint of pages, acceptance criteria, API endpoints, specs and source files, plus `git diff`. Pull requests run only the affected tests plus every P0 test; nightly runs everything. | Unit tests |
| 10.6 CI | One entry point, `python -m tools.ci.run --stage pr|nightly|release`. Templates in `ci/github-actions.yml` and `ci/azure-pipelines.yml`. Exit codes: 0 passed, 1 gate failed, 3 environment blocked. Reports, JUnit and traces are uploaded. | Unit tests for exit codes |

**Bugs found and fixed while building it**
- The health check looked for role login files under the wrong file name.
- Test-title matching in selective runs and in the non-functional generator broke on titles containing `",`.

**Bugs found and fixed in the end-to-end run**
- Quarantine counting, release and the report listing only ran when Phase 11 enhanced reporting was on. They now run
  on every report.
- With the app down, the health check waited for every role login to time out (97 s). The base-URL check now runs
  first (2.3 s).

**End-to-end CI benchmark** (`python -m tools.benchmark.ci_bench`): 15/15 checks pass. App down → exit 3; nightly
burn-in admits 5/5 with no order-dependent test; a PR with no change runs only the smoke test, and one edited spec adds
just its test; a release with a failing test exits 1, and exits 0 once that test is quarantined.

**Bugs the property tests found**
1. **Real bug in API test generation.** For decimal ranges, generated values are rounded to 2 decimal places. With a
   range of 0 to 0.016, the case meant to be accepted "at max" sends 0.02, which is above the max, so the test would
   fail on a correct app. Fix: use the bound's own number of decimals. Not fixed yet.
2. **Renderer property failure.** Not diagnosed yet; it may be a renderer bug or a wrong assertion in the test.

The property suite also needs trimming. It took 14 minutes while sharing the machine with the CI run.
