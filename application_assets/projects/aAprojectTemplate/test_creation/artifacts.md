# Test Creation Artifacts

This folder holds the structured artifacts produced by **Module 2** (Test Creation). These are the intermediate and output files between business-level comprehension and executable Playwright test specs. All files here are written by the pipeline — do not edit them manually.

---

## File inventory

### `test_suite.json`

The single source of truth for every generated spec and its status. Updated by ScriptGenerationAgent
after each spec is written, and `last_run`/`last_result` are stamped onto the matching spec by
ReportingAgent after every execution — that's also what feeds `test_catalog.csv`/`.md` below.

`spec_id` follows whichever scenario_id scheme `business_scenarios.json` used for that scenario —
legacy hyphenated (`BS-001`) or the current module-scoped form (`M01_BS_001`). Both are handled
identically everywhere downstream (execution result matching, healing, the catalog, suite resolution).

```json
{
  "project": "YourProjectName",
  "updated_at": "2026-06-01T10:00:00Z",
  "total_scenarios": 10,
  "new_additions": ["test_M01_BS_001_login.spec.ts"],
  "specs": [
    {
      "spec_id": "M01_BS_001",
      "scenario_title": "Successful Login",
      "module_id": "M01",
      "file": "M01/test_M01_BS_001_login.spec.ts",
      "status": "new",
      "tier_used": 0,
      "fallback_route": null,
      "generated_at": "2026-06-01T10:00:00Z",
      "last_run": "2026-06-02",
      "last_result": "passed"
    }
  ]
}
```

| `status` | Meaning |
|----------|---------|
| `new` | Generated by primary LLM — not yet run |
| `degraded_fallback` | Generated by Python fallback — needs review |
| `healed` | Fixed by HealingAgent via LLM |
| `healed_fallback` | Fixed by CSS-based fallback |

`tier_used`: `0` = primary LLM, `1` = NSHTTPConnector, `2` = Python fallback.

`fallback_route: "locator_validation_failed"` means ScriptGenerationAgent's live dry-run (see below)
caught the LLM inventing a selector, retried once, still failed, and fell back to the deterministic
generator — worth reviewing that spec by hand.

### `test_catalog.csv` / `test_catalog.md`

Human-readable, always-current view joining `business_scenarios.json` + `test_suite.json` — one row
per scenario, recomputed from scratch (not appended) on every script-generation run **and** every
execution/report run. Columns: `scenario_id, module_id, module_name, title, description, status,
last_result, spec_file, last_run`.

`status` here is about **generation**, not pass/fail — `no_test_yet` / `generated` / `missing_file`.
Real pass/fail lives in `last_result`, populated the first time that scenario actually executes. A
scenario that shows `status: generated` with a blank `last_result` simply hasn't been run yet.

---

### `intents.yaml`

DOM intents (`comprehension/dom_intents.json`) translated into a flat, scriptable action list. Written
by DiscoveryAgent early in the discovery step — despite the name, it lives here in `test_creation/`,
not under `comprehension/`.

---

### `scenario_element_map.json`

Maps each business scenario to the 3-7 DOM elements relevant to its steps. Produced by SemanticMapAgent in a single LLM call before script generation — prevents sending all 60+ DOM elements per scenario prompt. The `playwright_expr` value here is authoritative — it's resolved directly from the live DOM scan, never left to the LLM to guess.

```json
{
  "M01_BS_001": {
    "scenario_title": "Successful Login",
    "relevant_elements": [
      {
        "locator_id": "LOC-0003",
        "playwright_expr": "page.getByPlaceholder('Username')",
        "relevance": "primary username input — used in step 1"
      },
      {
        "locator_id": "LOC-0004",
        "playwright_expr": "page.getByPlaceholder('Password')",
        "relevance": "password input — used in step 2"
      }
    ]
  }
}
```

A scenario with zero relevant elements still gets an entry (`relevant_elements: []`) — ScriptGenerationAgent then relies entirely on the live locator dry-run below, since there's nothing pre-validated to hand the LLM.

---

## Live locator validation (ScriptGenerationAgent)

The LLM is instructed to use *only* the `playwright_expr` values above, verbatim — but an instruction
alone doesn't stop a model from inventing a plausible-looking selector. Two checks run on every
generated spec before it's trusted:

1. **Static check** — every `page.getByX(...)`/`page.locator(...)` call in the generated spec is
   compared against the scenario's allowed `playwright_expr` values. Anything not verbatim among them
   is logged as a warning signal (not a hard failure — wording drift can cause false positives here).
2. **Live dry-run** — headless-launches the module's page (running its `setup:` steps first if any),
   then actually resolves every locator call the spec references against the real DOM. Anything that
   matches zero elements fails.

On a live-dry-run failure: one retry, with the LLM told exactly which selector(s) didn't resolve. If
the retry still fails, the spec falls back to the deterministic Python generator (`fallback_route:
"locator_validation_failed"` in `test_suite.json`) rather than writing a script already known to be
broken.

## `test_scripts/` subdirectory structure

```
test_scripts/
├── test_SC-001_some_module_less_scenario.spec.ts   ← scenarios with no module_id sit flat here
│
├── M01/                       ← every M01 spec, grouped
│   └── test_M01_BS_001_login.spec.ts
│
└── M02/                       ← every M02 spec, grouped
    └── test_M02_BS_001_dashboard_load.spec.ts
```

Running `--module M01` scopes execution to `test_scripts/M01/`. A named suite (`--suite smoke`)
resolves its scenario IDs against `test_suite.json`'s `spec_id`/`file` fields and can pull from any
module's directory in one run — see `test_suites/test_suites.md`.

---

## File types allowed

`.json`, `.yaml`, `.csv`, and `.md` in this directory (`test_suite.json`, `scenario_element_map.json`,
`intents.yaml`, `test_catalog.csv`/`.md`). Test scripts are in `test_scripts/`. BRD inputs are in
`inputs/`.
